# 待辦走票，狀態由機器現算並掛固定頁面

## 問題

三張舊紙各管待辦的原始資料、狀態的算法與頁面的出口。若分開看，容易又在 repo（版本庫）裡手寫一份待辦或狀態，或只產出機器頁卻沒有固定入口。這一張把「資料在哪、怎麼算、去哪看」收成同一題。

## 選項

逐張的完整選項在 `docs/archive/` 的舊紙。待辦紙比較過 repo 裡的手寫待辦檔與 GitHub issue（GitHub 待辦票）；狀態紙比較過手寫 `docs/next.md`、現算但不進主線、現算後提交回主線；頁面紙比較過只把產物留在分支與用 GitHub Pages（GitHub 靜態頁面）掛固定網址。這三張沒有一個共同選項形狀，各自選的是票、現算不進主線、固定頁面。

## 決定

**待辦全走 GitHub issue，repo 不放手寫待辦檔（2026-09-09）。** 採第二個選項。一件事一張 issue，不是一張卡一張；暫緩規矩卡按「在等什麼」分組，標 `deferred-cards`，內文只列卡 id（識別名）與等待條件，規格留在 `blueprint/cards-38.json`。要拍板的題各開一張並標 `decision`，決策紙進 repo 後關票；立卡的 PR（合併請求）內文寫 `closes #N`，合併時自動關票。`handoff.md` 只寫現在在哪與該看哪些 issue，不列待辦。

**狀態頁不進主線（2026-09-09）。** 採第二個選項。一支進版控的程式從 git（版本控制）與 GitHub 現算里程碑進度線、開放的 PR 與 issue、每支檢查最近結果、主線領先落後；開工時由 SessionStart hook（開工掛鉤）算一次注入對話，每次併入主線由 CI（持續整合）算一次並推到只有機器寫的專門分支，歷史全留，不排 cron（定時工作）。里程碑與任務單由人放在 GitHub Milestones（里程碑）與 issues，位置由機器算。這張舊紙原先保留「下一步意圖」最多 20 行；同日的待辦紙以「repo 內不再有手寫待辦檔、`handoff.md` 不列待辦」收掉那個位置，現行決定是不保留手寫下一步意圖。

**機器算出的狀態頁掛 GitHub Pages（2026-09-09，2026-09-10 啟用）。** 採第二個選項。狀態程式產出 HTML（網頁檔），推到 `status` 機器分支；GitHub Pages 對著該分支根目錄提供固定網址 https://neknufelet.github.io/aosr-v3/ 。每次併入主線由 CI 重算重推，頁面仍顯示里程碑進度、開著的 PR 與 issue、每支檢查最近結果、主線領先落後。只有機器透過 `.github/workflows/status.yml` 寫該分支，歷史保留且不做 force push（強制改寫）；程式住在 `governance/status/`。

## 為什麼

事故 `status-file-grows-into-history-ledger` 曾讓同一份進度檔同時寫「已併回」與「未併回」，還留下 37 條劃掉項目；`index-docs-recopy-facts-that-drift` 則是原始資料已變、手抄文件沒變。待辦有票的開關狀態，狀態可從版控與平台現算，兩者都不需要再抄一份會過期的檔。算出的頁不進主線，但人仍需隨時看得到，所以用只讀機器分支的固定頁面承接。

## 代價

- 待辦紙的代價：離線看不到待辦，靠機器現算的狀態頁補足。
- 狀態紙的代價：沒有開工掛鉤的工具要手動跑一次狀態指令；舊 BASELINE 2.1.1 的 `docs/next.md` 做法不適用於這裡。
- 頁面紙的代價：repo 是 public（公開），狀態頁也公開；Pages 的啟用是 GitHub 設定，不在版控。舊紙補寫時頁面與程式尚未上線，2026-09-10 才啟用。
- 合併帶來的代價：待辦來源、狀態算法與展示出口在機器眼裡成為同一題；之後其中一題要翻案，得取代整張並重帶其餘仍有效的決定。
