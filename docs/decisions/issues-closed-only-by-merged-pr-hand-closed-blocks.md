# 票只由合進主線的合併請求關，人手關票會被重開並擋合併

## 問題

第一張舊紙關掉人手收票的路：沒有合進主線的關票 PR（合併請求），守衛就重開。第二張舊紙再補上合併門口的牙，避免事件漏送或守衛壞掉時票一直關著。兩張其實是同一條規則的即時層與合併層，還要和狀態頁的事後層一起讀。

## 選項

逐張的完整選項在 `docs/archive/` 的舊紙。第一張比較過維持狀態頁紅字，或在票被關時查關票來源、沒有合進主線的 PR 就重開。第二張比較過維持「守衛加狀態頁」、升成擋合併的規矩卡並准它上網讀 GitHub、或要求人在版控裡留一份會漂的關票憑證。

## 決定

**票只准由合進主線的 PR 關，人手關的由機器重開（2026-09-10，決策票 #83）。** 採第二個選項。要關票就在 PR 內文寫 `Closes #n`，由 GitHub 在該 PR 合進主線時關票並記下兩邊連結。`.github/workflows/issue-guard.yml` 在 `issues: [closed]` 事件叫起 `governance/status/issue_guard.py`，用 GraphQL（圖形查詢語言）的 `closedByPullRequestsReferences` 查關票來源，並與狀態頁共用查詢；有合進主線的 PR 就不動，沒有就用 `gh issue reopen` 重開並留言說明正確關法。`gh`（GitHub 命令列工具）不在、平台無回應或資料形狀看不懂時，一律離開碼 2，不重開、不留言。狀態頁繼續顯示「關掉的票能否串到綠收據」，守的是更長的鏈。

**人手關的票超過零張就擋合併（2026-09-10，決策票 #89）。** 採第二個選項。規矩卡 `governance/rules/issues-closed-only-by-merged-pr.toml` 的 `declared_level = "blocking"`，掛在 `verify` 工作；它逐張讀 GitHub 自己記的關票來源，不把票面互相提到當成落地。人手關的票超過 0 張就回 1。這是第二支准上網的檢查；每支例外各有一張紙、一筆 `[[settings.allow]]`，含 `reason` 與 `expires`，由 `exemptions-need-expiry` 守。這一筆到期日是 2026-12-08，缺席或過期就回 2 且不上網。

這支檢查只讀關掉的票與掛著關票的 PR；CI 自帶 token（存取憑證）只給 `contents: read` 與 `issues: read`，重開票所需的寫入權限只在守衛自己的 workflow（工作流程）。欄位名、查哪些格與「PR 是否已落地」共用 `governance/status/collect.py`；只有主線分支名從卡的 `[settings]` 來，讓樣本樹可替換。具名放過某張票也寫在同一張表，必須帶票號、理由與到期日，過期視同沒有放行。

三層分工固定：`governance/status/issue_guard.py` 在事件發生時重開；`issues-closed-only-by-merged-pr` 每次合併檢查重數並擋門；狀態頁顯示關票是否串到綠的雲端收據。第二張紙把「只准一支檢查上網」改成兩支具名例外，沒有把通則放寬。

## 為什麼

上一代的事故形狀是「票關了，東西沒落地」。平台在合併時寫下的關票來源是可回查的事實，人的手寫憑證不是。即時守衛最快但依賴事件；合併卡慢一步，卻每跑重數、不依賴事件；狀態頁不擋門，但能看更長的收據鏈。三層各守一段，少一層就留下一條漏路。

## 代價

- 第一張舊紙的代價：只改文件的決策票也必須用一個 PR 合入文件來關。事件若漏送或守衛壞掉，票會暫時保持關閉，靠另外兩層補。守衛有 `issues: write`，是 repo 裡第一支會改 GitHub 狀態的機器，且只有那份 workflow 擁有該權限。
- 第二張舊紙的代價：檢查與後設測試 6 回合都依賴網路與 token；本機斷網時檢查回 2。准上網的檢查由一支變兩支，第三支要不要放行必須另開紙。立卡當天量到主線有 22 張關閉票，每張都對得到合進主線的關票 PR，人手關票為 0；若雲端列出例外，處置是重開再由 PR 關，不是新增放行。一張票掛著上百個關票 PR、單頁看不完時回 2；票變多會讓查詢變慢，但程式必須翻到底。
- 合併帶來的代價：即時重開與擋合併在機器眼裡成為同一題；之後其中一層要翻案，得取代整張並重帶其他仍有效的層。
