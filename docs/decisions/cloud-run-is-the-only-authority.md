# 雲端那一跑是唯一權威，本機收據只是宣稱

## 問題

兩條候選規矩打架：「終審不必自己重跑，信下游的收據」與「只有雲端那一跑的收據算數，自報的不算」。另外派工工具在本機跑，第一張真實收據一定是本機產的，若「只認雲端」套在所有席位，第一天就要開豁免。

## 選項

1. 所有席位都只認雲端收據；本機收據一律無效。
2. 只有驗收席的收據必須來自雲端；工人與找碴席的本機收據仍算數。
3. 權威只有一個——雲端那一跑（GitHub Actions 的 run，有 run id、有 log）；本機收據可以存在、可以記，但欄位標明 `authority = "claim"`（宣稱），沒有裁決權。終審不重跑，因為它看的是雲端那一跑的結果，不是任何人自報的數字。

## 決定

選項 3。老闆原話：「我比較想要用雲端收據，這應該是我理解比較合理的 PR、CI 的方式，其他的配置應該要圍繞這個需求修改。」

具體：
- 收據的 `authority` 欄只有兩個值：`cloud-run`（必附 GitHub Actions run id，機器可回查）或 `claim`。沒有第三種，也沒有「本機但算數」。
- 「終審不必自己重跑」保留為知識、不是規矩：指揮不重跑，是因為裁決已由雲端那一跑做完；指揮只親自重跑票上具名的高風險斷言（照「分工五席」）。
- 工人交付時可以附本機跑的結果當參考，但 PR 合不合只看雲端。
- 不需要豁免：本機收據從第一天就是 `claim`，不是違規。

## 為什麼

v2 事故 `builder-grades-own-work-edits-ruler`（7 次復發、嚴重度 5）：施工者自報數字、自己改尺。`verifier-trusts-self-reported-fields`：驗證器信自報欄位，九起收據假綠。兩筆的共同病根是「裁決權落在自報那一方」。把權威收到雲端那一跑，誰來改都一樣被擋，不需要「守衛的守衛」。

## 代價

- 雲端跑不到的東西（GPU、長測試、本機才有的工具）沒有權威收據，只能是宣稱；要它算數就得搬上雲端或自架 runner（照「只有雲端檢查算數」的第二層）。
- 收據的產生器今天還不存在，`receipt-authority-is-the-cloud-run` 那張卡改為等 `receipts-exist`。
- 連帶要回答的：`merge-gate-read-back`（合併門口設定要從 GitHub 回讀比對）要不要准 CI 上網讀 GitHub 自己的設定——另開題，不在這張紙裡決定。
