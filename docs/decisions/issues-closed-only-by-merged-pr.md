# 票只准由合進主線的 PR 關，人手關的由機器重開

## 問題

票（issue，GitHub 上的待辦票）現在有兩條關法：PR（合併請求）內文寫 `Closes #n`，合併時 GitHub 自己關掉並記下「是這個 PR 關掉它的」；或者人手 `gh issue close`、網頁按一下關掉。第二條關法背後可以什麼都沒有——票關了，程式沒進主線。狀態頁上「關掉的票對不對得到綠收據」那一格已經把人手關的票列成紅字，但那是事後給人看的一句話，擋不住當下那一下。

## 選項

1. 維持現狀：只靠狀態頁那一格紅字，人自己記得不要手關。
2. 把人手關這條路直接關掉：票一被關，機器就去問 GitHub「有沒有一個合進主線的 PR 掛著關掉它」，沒有就當場重開並留言。

## 決定

選項 2。
- 票只准由**合進主線**的 PR 關掉。要關一張票，就在那個 PR 內文寫 `Closes #n`，合併的時候 GitHub 會自動關，順手把兩邊連起來。
- 人手關掉（`gh issue close`、網頁按關閉）的票，由 `.github/workflows/issue-guard.yml` 掛 `on: issues: [closed]` 事件叫起 `governance/status/issue_guard.py`：它問 GitHub 記的關票來源（GraphQL 的 `closedByPullRequestsReferences`，跟狀態頁那一格共用同一句查詢，不抄第二份），有合進主線的 PR 就什麼都不做；沒有就 `gh issue reopen` 重開，並留一句人話說明票只准由 PR 關。
- 問不出答案就不動手：`gh` 不在、GitHub 回不了話、回來的形狀看不懂，一律離開碼 2，不重開也不留言。分不清的時候亂重開，比漏掉一張更糟。
- 狀態頁那一格保留，它是第二層——給人看的紅字，管的是「關掉的票串不串得到綠收據」這條更長的鏈，不是這一支的替身。

## 為什麼

上一代出過的事就是「票關了、東西沒真的落地」：關票是一個動作，落地是另一件事，兩者之間只有人的習慣。習慣不是機器守得住的東西。GitHub 自己記的關票來源是機器記的事實（合併時它自己寫下的連結），拿它當判準就不必猜；而「重開」這個動作是可逆的、代價極小，誤判一次的成本只是有人要再走一次 PR。

## 代價

- 決策類的題也要有 PR：想關一張只需要寫紙的票，也得開一個 PR 把紙寫進去，靠那個 PR 關它。寫這張紙的那個 PR 就是關掉這一題的 PR。
- 機器重開靠 GitHub 的事件（`issues: closed`）。事件漏送、或那一跑自己壞掉的時候，票就會停在關掉的狀態——那一格由狀態頁的紅字補上，兩層都漏才會真的看不見。
- 這一支拿得到寫票的權限（`issues: write`），是這個 repo 裡第一支會回頭改 GitHub 上東西的機器。寫的那一格只有這一個、只給它自己那一份 workflow；同一份裡另外宣告的 `contents: read` 是唯讀，checkout 拿程式碼要用。
