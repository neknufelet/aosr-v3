# 工作樹跟派工資料夾住一起，開與拆只走一支工具

## 問題

worktree（同一個 repo 的第二個工作目錄，一張票一棵）放哪裡、叫什麼、誰來拆。2026-09-19 量到的現況：
三棵樹丟在 `~/ghq/` 根層（那一層是別的專案的地方）；同一張票的派工資料夾、樹、分支三個名字對不起來
（`345-timbre`／`aosr-v3-345-timbre`／`feat/345-timbre-evaluator`）；票合了樹與分支沒人收，本機留著 77 條分支。
位置與名字沒有寫下來的規矩，靠每個對話自己記。

## 選項

1. 樹放 repo 裡面的隱藏目錄（例：`.worktrees/`）。
2. 樹放 repo 旁邊另開一個目錄。
3. 樹跟派工資料夾住一起：`~/aosr-v3-work/<票號>-<短名>/tree`。

## 決定

選項 3。一張票一個資料夾 `~/aosr-v3-work/<票號>-<短名>/`：工單與證據放那一層，樹住它底下的 `tree/`，
分支叫 `<種類>/<票號>-<短名>`，種類只認 feat、fix、docs、card、chore。資料夾、樹、分支三樣東西一個名字。

開樹、列樹、拆樹只走 `governance/worktrees.py`（`new`／`list`／`remove`），不再手打 `git worktree add`。
拆樹有兩條路，分支那一格任一條成立，再加上樹的兩格都成立才拆：

- 開過 PR（合併請求）的：這條分支的 PR 已經合進主線（合進別條分支的不算）、本機分支的頭等於 PR 的頭。
- 沒開過 PR 的（#442，2026-10-06 加）：`list` 與 `remove` 先更新 origin/main，再確認分支上沒有任何一顆主線之外的提交。
  不要求分支的頭等於最新主線：主線往前走了，從舊主線開出來、什麼都沒做的樹照樣能拆。
  已經有 PR 的分支不走這一條，照第一條判；這一格也不用在開過 PR 的分支上（主線用 squash 合併，合過的分支上原本那幾顆提交本來就不在主線裡）。
- 樹的兩格：樹裡沒有改過、暫存或沒進版控的檔，也沒有標成不追蹤改動的檔（git status 看不到它們的改動）；被 `.gitignore` 蓋住的檔只有重建得回來的那幾種（環境、快取、本機那份測試收據，沿用原本那張清單）。

PR 查不到、git 量不下去、主線更新不了，一律停，不當成沒有 PR、也不當成零顆提交。
`list` 說「該拆」與 `remove` 真的去拆，問的是同一組條件：PR 合了但本機還有沒送出去的提交的樹，`list` 寫的是「別硬拆」。
沒開過 PR、符合條件的樹，`list` 只印「符合清理條件」，不標紅、不自動拆：剛開好的樹也長這樣，那張票的工作有沒有停，要人確認過再走 `remove`。
不新增強制拆除。拆的是 `tree/` 與本機分支；派工資料夾裡的工單與證據留著。不符合條件的樹這支工具不碰，要人看過再處理。

## 為什麼

v2 的事故 `accumulating-disk-state-has-no-owner`：工作樹累積到 111 棵 67 GB、5 棵髒樹沒有人認，
因為沒有一個地方說得出「這一棵是哪張票的、可以拆了沒」。住在票的資料夾裡，這兩題看路徑就有答案。

不放 repo 裡面：掃描工具、測試收集、搜尋都會掃進那個目錄，同一批檔算兩次；v2 還有一筆是在某一棵樹裡
跑起來的直譯器 import 到另一個 checkout 的程式碼。不留在 `~/ghq/` 根層：那一層的規矩是「網站／擁有者／repo」。

主線用 squash（把整條分支壓成一顆提交）合併，`git branch --merged` 看不出一條分支合了沒，所以拆樹去問 GitHub，
而且要比頭：合了之後本機又多提交的分支，拆掉就是丟工作。沒進版控的檔原本交給 git 自己擋（#442 起工具先量，git 是第二道），工具不加強制旗標；
但 git 的「乾淨」不看被忽略的檔、拆樹時會無聲一起刪掉（2026-09-19 找碴時實測），所以那一格工具自己先量，
量到清單以外的被忽略檔就不拆、把檔名印出來。

施工的工人沙箱只准寫自己的工作目錄，開不了樹；會開樹的只有主對話，所以一支工具加入口檔一行就管得到全部的開樹動作。

沒開過 PR 那條路（#442）：原本只認「PR 已合」，所以停工、量測用、從沒提交過的樹拆不掉，只能留著或手動硬拆（2026-10-06 有三棵卡著）。
它的風險是丟掉沒送出去的工作，所以守的是「分支上沒有主線之外的提交」與「樹乾淨」兩件事，而不是「分支的頭等於最新主線」——
後者在主線往前走之後永遠不成立，等於沒開這條路。

## 代價

這不是規矩卡：雲端看不到本機的樹，合併門口守不到。守得到的只有 `list` 把放錯地方、名字對不上、該拆沒拆的
標出來並回非零——要有人去跑它。手打 `git worktree add` 到別的地方，要等下一次 `list` 才看得見。
`list` 與 `remove` 要問 GitHub，沒有網路就做不了，會明說做不下去並回「這一跑不算數」的離開碼，不當成沒事。
「重建得回來的那幾種」是寫在工具裡的一張短清單：樹根層的環境與工具快取目錄、任何一層的位元組碼快取目錄、
本機那份測試收據的目錄；清單以外的被忽略檔一律擋。有人硬把要留的東西放進那幾個目錄裡，工具擋不到。
stash（暫存起來的改動）存在共用的地方，拆樹不會弄丟它，但它會跟那張票脫鉤，工具不管這件事。
只剩操作紀錄（reflog）找得到的提交（例如提交後又 `reset --hard` 退回去）不在任何分支上，工具量不到；拆樹之後它沒有任何參照指著，等 git 清垃圾就沒了。
派工資料夾本身（拆樹之後留下的工單與證據）什麼時候清，這張紙沒有管。
`list` 與 `remove` 每次都先更新 origin/main，多一次對 GitHub 的請求；沒有網路就做不了，照前面講的停下來。
「符合清理條件」只量得到提交與檔案；那張票的工作是不是真的停了（例如施工者正在一棵還沒改任何檔的樹裡跑），工具看不出來，要人確認。

## 拍板

老闆，2026-09-19 對話：位置同意選項 3，並指定「連同拆 worktree 一起」收進同一支工具。票 #364。

2026-10-06，票 #442，老闆送出的訊息（逐字）：

> 同意修改 #442，新增「未開過 PR、沒有主線之外提交」的安全拆樹路徑。
>
> 不要求分支與最新主線的 head 相同；更新 origin/main 後，確認分支沒有主線之外的提交即可。工作樹須乾淨，並沿用既有被忽略檔案白名單。PR 查詢或 Git 檢查失敗一律停止；已有 PR 的拆樹規則不變，不新增強制拆除。
>
> 修改原決策紙、工具與測試，放同一支 PR，不另增一張決策紙。list 與 remove 共用資格判斷，但「符合清理條件」不等於自動清理。測試至少守住：主線已前進的空樹可拆、有獨有提交或任何未保存資料不可拆、查詢失敗不可拆，以及原本已合併 PR 的路徑不退步。
>
> 合併後，逐棵重新檢查 440、585-step5、608；確認相關工作已停止且條件全部成立，再由工具拆除。只刪工作樹與本機分支，外層工單、證據保留。

主對話補的落地細節（不是老闆原話）：「樹乾淨」包含暫存的改動，而且兩條路都由工具先量、把檔名印出來（原本未進版控的檔交給 `git worktree remove` 擋，現在那仍是第二道）；`list` 對符合條件的樹只印一行、不標紅，因為剛開好的樹也符合；標成不追蹤改動的檔也算沒保存的資料、一律擋（審查時找到 git 與工具原本都看不到它們的改動）；量樹時不搶索引的鎖，免得施工者剛好提交時失敗。
