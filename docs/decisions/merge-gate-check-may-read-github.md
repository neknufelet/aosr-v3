# 合併門口那一支檢查准上網回讀 GitHub 的 ruleset，只准這一支、只准讀，放行有到期日

## 問題

卡 merge-gate-read-back 要的是「合併門口的設定要從伺服器回讀比對」：主線的 ruleset 是不是 active、必要檢查是不是 `verify`、不准刪、不准非快進、走 PR 且新提交作廢舊核准、沒有人能繞過。那些設定只住在 GitHub 上，檢查程式得在 CI 裡上網讀，跟「檢查不上網、只認雲端收據」的 hermetic（不依賴外部網路）主張直接衝突。這是 issue #9 那一組剩下的最後一張，決策紙「雲端那一跑是唯一權威」的代價段明寫另開題（issue #64）。

先測過（2026-09-10，記在 #64）：repo 是公開的，`GET /repos/{owner}/{repo}/rulesets/{id}` 與 `/rules/branches/main` 不帶任何 token 都回 HTTP 200、內容完整。所以「CI token 讀不讀得到」「要不要 admin 權限」兩個問號都消掉，剩下純規矩題。

## 選項

1. 准這一支檢查上網，但只准這一支、只准讀，卡上登記為放行並寫到期日；讀不到（`gh` 不在、沒登入、API 回不了話）回 2 不回 0。
2. 不上網。ruleset 的期望值寫成檔進版控，靠人在改設定時同步；卡改成只比對那份檔的形狀，實際設定漂了抓不到。

## 決定

選項 1。老闆原話（2026-09-10）：「選 1，90 天，和之前好像有另一個也是 90 天，一起審」。

具體：
- 放行登記在卡 merge-gate-read-back 的 `[[settings.allow]]`，帶 `reason` 與 `expires`，由規矩卡 exemptions-need-expiry 守。到期日**對齊第一批放行那一天**（今天樹裡最多筆的那個到期日），不是從今天起算的第 90 天：一個審查日一次看完所有放行，不要每筆各自漂一天。
- 放行有牙：檢查程式自己讀那一筆放行，缺席或過期就回 2、不上網。到期那天不只 exemptions-need-expiry 紅，這支檢查也拒絕上網。
- 只准讀。檢查程式只打讀的 API，不改任何設定；token 用 CI 自帶的 `GITHUB_TOKEN`，權限照舊 `contents: read`。
- 期望值全部住在卡的 `[settings]`：哪個 repo、哪個 ruleset、必須有哪幾條規則、必要檢查叫什麼、bypass 名單必須是空的。改期望走 PR。
- 別的檢查照舊不准上網。這張紙只放行這一支，不是開一條「有理由就可以上網」的通則。

## 為什麼

v2 事故 `enforcer-declared-but-never-installed`：規矩宣告了，合併門口沒真的裝上，紅的照樣合進去。`amended-a-pushed-commit`：推過的提交被改寫，歷史被動。兩筆的共同病根是「版控裡寫的期望」與「伺服器上真的設定」沒有機器在比。選項 2 抓不到伺服器那一端漂掉，等於只守了一半；而伺服器那一端正是事故發生的那一端。

## 代價

- 這支檢查與它的後設測試六回合從此依賴網路與 GitHub 的 token：本機斷網跑 pytest，第一回合會紅（檢查回 2，第一回合要 0）。雲端那一跑才算數，本機本來就只是宣稱，但要知道這是刻意的。
- `verify` 那個 job 要多一個環境變數把 CI 自帶的 token 交給 `gh`，否則 `gh api` 拒跑。
- 期望值住在卡上，改 GitHub 設定的人要同時開 PR 改卡，不然下一跑紅。這是要的效果，不是副作用。
- 必紅樣本的形狀是「卡上期望跟伺服器不一致」（樣本的卡宣告一個伺服器上永遠不會有的必要檢查名），控制樣本是「登記的 ruleset id 伺服器上不存在」。兩種都要上網才判得出來。
- 放行到期那天要有人重新看：還要不要這支檢查上網、範圍有沒有變寬。續期改卡與每一份樣本樹裡複製的那筆。
