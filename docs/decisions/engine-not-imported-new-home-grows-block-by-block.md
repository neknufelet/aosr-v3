# 舊引擎不搬進來，新家 src/aosr 一塊一塊重新長

## 問題

2026-09-11 早上那張紙（`docs/decisions/engine-tree-lands-unwatched-then-rules-bite-one-by-one.md`）
拍的是：把上一代的引擎樹整棵鏡像進 `src/`，七張規矩卡先在掃描面上宣告「這棵樹別看」，
之後一張卡一個 PR 把規矩一條一條放進去咬。那張紙的第一段當天就合進主線（七張卡加了 `!src`、
根層白名單加了 `src`、pytest 的模組搜尋路徑加了 `src`），第二段（真的搬樹）做到一半沒有合。

同一天下午老闆把那個前提推翻了：**他要的不是「先搬進來再慢慢管」，是「v3 裡永遠只有新家」**。
所以真正的題目不是「怎麼搬」，是**上一代的引擎程式碼到底要不要進 v3**——
早上那張紙把這一格當成已經定案，直接跳到「搬進來之後怎麼辦」。

## 選項

1. **進版控當隔離區**（早上那張紙）：整棵樹鏡像進 `src/`，七張卡先別看，再一條一條放進去咬。
2. **拉進來但不進版控**：磁碟上有那棵樹、git 裡沒有，靠忽略清單擋住。
3. **submodule**（子模組，用一個指標把另一個 repo 的某個記號掛進這棵樹）：指向上一代那個 repo 的凍結記號。
4. **完全不進**：v3 裡只有新家，一塊一塊重新長，只帶那一塊的測試與標準答案。

## 決定

**選項 4。** v3 裡從頭到尾只有新家 `src/aosr/`（套件名 `aosr`），上一代的引擎程式碼一行都不進來
——不進 git，也不用忽略清單拉進磁碟。

- **一塊＝上一代引擎底下一個子套件＝一張票**；一張票底下拆成幾個 PR，每個 PR 雲端 `verify`
  （GitHub Actions 上那個擋合併的檢查工作）綠了才算。第一塊是 `config`（票 #127）。
- **帶進來的只有那一塊的測試與標準答案**：測試的 import（引用路徑）要改成新家的名字，
  **寫死的期望值一個字都不准放鬆**。行為必須跟上一代的數值一致，結構隨便改。
- **原料鎖住才准開工**：上一代那個 repo 打一個記號 `v3-donor`、整個 repo 設成唯讀（票 #123）。
  工人只准從那個記號開一棵**唯讀的臨時工作樹**去讀原料，讀完就丟，不准把原料提交進 v3。
- **新家從第一塊起就被現有的規矩全咬**：早上那七條 `!src` 排除在新方向下沒有對象，
  這個 PR 一起拿掉（票 #113 到 #119）。印不動再談改卡或立新卡，而且要帶實跑的數字，
  不准先開排除再說。`src` 留在根層目錄白名單與 pytest 的模組搜尋路徑裡——那兩格是新家要用的。
- **沒有裁判的不准關票**：一塊裡哪些公開函式沒有寫死期望值的測試，要在那張票上列出來；
  列著沒補完，那張票不准關。
- 三張還沒立的卡與兩件沒解的事各有票，不寫進這張紙：#125（新家分層——下層不准 import 上層、
  不准成環）、#126（單一 .py 檔的行數上限）、#120（引擎測試什麼時候、以什麼形狀進雲端 `verify`）。

## 為什麼

- **老闆怕新舊混血。** 半棵舊樹躺在版控裡，下一個人分不出哪一支是要留的、哪一支是等著被取代的；
  而「等著被取代」這件事沒有機器看得見。完全不進就沒有這個模糊地帶：樹上的每一支都是新家的。
- **選項 2 直接踩在一筆 v2 事故上。** `accumulating-disk-state-has-no-owner`
  （磁碟上的東西沒有主人）那筆記的正是「有東西在磁碟上、沒有進版控、沒有人負責清」的形狀。
  選項 3 是同一個病加一層工具：子模組指到哪一個記號、有沒有跟著更新，同樣不在這棵樹的檢查面上。
- **早上那條路的代價是一次性、不可逆的。** 那張紙自己就寫了：七條排除沒有到期日、
  上一代那七萬多行會永遠留在 v3 的版控歷史裡，而且連 `secrets-never-committed`
  （機密不准進版控那張卡）都掃不到它——那張卡的排除同時濾掉工作樹與歷史物件。
  不搬就沒有這一筆：新家的每一行從第一天起都在那張卡的掃描面上。
- **「只帶測試」不是省事，是換一種貴法。** 別家模型唯讀實測（另一家模型只讀不寫、帶命令與輸出的那一輪）
  量到上一代的測試樹是 357 支測試檔、179,184 行，其中 **94 支直接 import 週邊腳本那一包**；
  子套件之間有 **11 組雙向依賴**（`config` 與材料那塊互引、物理與計分那塊互引等等）。
  照抄搬不動，這是選項 4 反過來的好處：一塊一塊長的時候，那些環是**當場要切掉的東西**，
  不是搬完之後才發現的債。相關的 v2 事故是 `core-layer-imports-orchestration-layer`
  （核心層反過來引用編排層）。
- **新舊之間的證據只能靠數值對照。** 老闆拍板每一塊都要做：上一代那邊跑一次、新家這邊跑一次、比。
  搬樹那條路不需要這件事（因為是同一份程式），重新長就必須有；這是選項 4 唯一站得住的品質保證。

## 代價

- **只能照依賴順序長，而那個順序今天是有環的。** 別家模型唯讀實測：11 組雙向依賴；
  第一塊 `config` 不是乾淨的葉子——它反過來依賴別的子套件，收斂在 **6 支檔**，
  而且沒有一處是只在型別檢查時才成立的護欄，全是模組層的真 import。
  所以第一塊不是照抄，是要當場把那 6 處切斷，切法寫在 #127。
- **每一塊的測試都要改 import，而且有一批帶不過來。** 那 94 支 import 週邊腳本的測試，
  在「只帶測試」這條路上收不進來（那一包本身有 29 個檔、32,938 行，別家模型唯讀實測）。
  今天不假裝有解：那一格的處置寫在 #127 與 #120，不寫在這張紙上。
- **標準答案要從接近零長出來。** 上一代的 `tests/golden` 底下只有 2 個 json（別家模型唯讀實測），
  也就是說「每一塊一份標準答案」等於新寫十一份。沒寫期望值的測試那一塊就是沒有裁判，
  票上要列出來、沒裁判不准關票——這一條靠人看，沒有機器在守。
- **新家一開始就被 27 張卡全咬，會很痛。** 別家模型唯讀實測：上一代那棵樹裡，
  函式行數超過現有門檻的有 **165/1898 支**（其中物理那塊佔 97 支），分支數超標的只有 4 支。
  重新長的時候結構可以改，所以這些不是直接繼承的債；但它是一個訊號——
  「先用同一把尺、印不動再談改卡」這句話會很快被逼到檯面上，而每一次談都是一張票。
- **單一檔案的行數上限今天沒有卡在守。** 老闆拍板要有（上一代最大的引擎檔 3,448 行，
  別家模型唯讀實測），而現有 27 張卡裡一張都沒有量過 .py 的檔案大小。那是 #126，還沒立。
- **引擎測試進雲端那一格沒解。** v3 今天的鎖檔裡數值計算那個框架是 0 筆（別家模型唯讀實測），
  而上一代的測試自己記著「牆上時間由編譯主導」、還持一把全機的檔案鎖。
  切分層與 15 分鐘那條線怎麼辦是 #120；在它拍板之前，新家的測試只跑得起本機那一份。
- **鎖還沒上。** 別家模型唯讀實測：記號 `v3-donor` 今天**不存在**，
  而且上一代那個 repo 的 HEAD 比它現有的凍結記號多 3 筆提交。
  「沒鎖住之前不准開工」是這張紙的前提，前提今天還沒成立——那是 #123，要先做完。
- **以後要回頭查上一代怎麼寫的，只能去那棵唯讀樹。** v3 的版控歷史裡不會有它，
  也就不會有「在 v3 裡 grep 一下就找得到」這件事。這是選擇不做，不是做不到。
- **早上那張紙已經合進主線一次了。** 這張紙推翻它、同一天第二次動同一批卡面，
  代價是卡面的註解與 `pyproject.toml` 的排除清單在一天之內改了兩次；
  兩張紙都留著（舊那張標成 superseded），為的是往後看得出這個轉彎真的發生過。

## 拍板

老闆，2026-09-11 下午對話（票 #124）。「上一代的程式碼不進 v3、只帶測試與標準答案」、
「v3 裡永遠只有新家」、「一塊＝一個子套件＝一張票」、「先用同一把尺、印不動再談改卡」、
「沒鎖住快照之前不准開工」，都是那一次當場拍的。
