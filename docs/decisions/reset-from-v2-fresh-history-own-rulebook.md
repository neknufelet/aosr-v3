# 從 v2 事故重長，歷史清空，v3 先自建規矩本

## 問題

三張舊紙處理同一次重啟的三個面向：工作樹留下什麼、版本歷史是否也清掉、以及新規矩先在本專案試還是直接改共用總本。拆開後容易只刪檔卻保留舊歷史，或一開始就讓其他專案一起承受尚未跑過的新規矩。

## 選項

逐張的完整選項在 `docs/archive/` 的舊紙。清空紙比較逐份整理半成品與只留事故資料、藍圖後重長；歷史紙比較保留歷史並在新提交刪檔，與用無父節點初始提交且刪除遠端版本庫後同名重建；規矩本紙比較直接升共用總本讓四個專案一起跟，與先在 v3 自建自測、跑順才上提。

## 決定

**清空重來，規矩從 v2 事故資料重新長（2026-09-09）。** 採第二個選項。清空當下只留 `v2-audit/`、`blueprint/`、`DIRECTION.md` 與 `handoff.md`；往後每張規矩卡都要對回 `v2-audit/lessons.json` 的一筆事故，或明白標示沒有 v2 血債。清空的是當時的 13 張規矩卡、15 支檢查、8 張決策紙與半成品，不為保留它們扭曲新規矩。

**git 歷史重來，GitHub repo 刪掉重建（2026-09-09）。** 採第二個選項：用 `git checkout --orphan` 建無父節點的 initial commit（初始提交），刪掉整個 GitHub repo（遠端版本庫）後同名重建，藉此清掉舊的 5 個提交與 3 張已合併 PR（合併請求）。主線 ruleset（規則組）id `22615925` 重新設成不准刪分支、不准改寫歷史、只能透過 PR 進主線。唯一刻意差異是先拿掉 required status check（必要狀態檢查）`verify`，避免檢查程式已清空時所有 PR 永遠卡住；第一張有牙的卡由 PR #19 合入，主線 `verify` 跑綠後，2026-09-09 已加回。

**v3 自建規矩本，跑順再上提（2026-09-09）。** 採第二個選項。v3 在 `governance/` 自建規矩卡、平台慣例、範本三區，內容全新、版號從 3.0.0 起；舊 BASELINE 2.1.1 與其他專案不動。9 個 skill（流程技能）留在 AI_TOOLS（共用工具庫）作唯一來源，v3 使用但不複製進 repo；要改就改共用來源。派工工具 `calling-other-models` 照用，其餘流程技能在 v3 先不呼叫，以分工五席取代，但不搬、不改。跑順後把整個規矩資料夾搬到 standards repo（共用標準版本庫）成為新版；每個專案明寫所釘版本，升版用一個 PR，不自動跟進。

## 為什麼

半成品的維護成本已超過價值，保留又會讓後來的規矩不斷遷就舊形狀。若舊歷史仍在，5 個提交與 3 張 PR 仍會被拿來當參考，清空就不完整；但沒有任何會咬的檢查時先鎖 `verify`，只會造出永遠過不了的門。共用總本當時連一支檢查都沒有，直接讓四個專案一起跟是紙上談兵；先在 v3 跑順、各專案釘版本，才能避免抄三份、漂三份。

## 代價

- 清空紙的代價：舊 13 張卡與檢查程式消失，只剩規格描述在 `blueprint/convergence-result.json` 與 repo 外的備份（`~/aosr-v3-blueprint-2026-09-09/`，含完整 git 歷史 bundle）。
- 歷史紙的代價：舊歷史只剩備份 bundle（`~/aosr-v3-blueprint-2026-09-09/aosr-v3-full-history.bundle`），GitHub 上找不到。
- 規矩本紙的代價：試驗期 v3 與其他專案規矩不一致，上提時要做一次遷移；流程技能不在 repo 內，換機器要先裝共用工具庫。
- 合併帶來的代價：清空內容、清空歷史與先自建後上提在機器眼裡成為同一題；之後其中一題要翻案，得取代整張並重帶其餘仍有效的決定。
