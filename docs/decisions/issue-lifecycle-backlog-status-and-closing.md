# 票的一生：待辦與帶回的結論都進票、狀態由機器現算、票只由合進主線的合併請求關

## 問題

一張票（GitHub issue，待辦票）的一生原本分在三張紙：待辦與狀態一張、在外面產生的結論怎麼帶回一張、票怎麼關一張。分開讀時，「討論後不做的票怎麼關」「決策票什麼時候關」要讀的人在兩張紙之間自己拼，而兩張紙寫的時間不同、字面不一致。

原本的題各是：
- 待辦要不要放在 repo（版本庫）裡的手寫檔。
- 討論 fork 出去（另開的對話、別的模型、外部報告）產生的結論怎麼帶回、放哪、算不算數。
- 進度與檢查狀態要不要手寫、算出來的頁面放哪、從哪個固定入口看。
- 人手關票怎麼擋；即時守衛漏了或壞了怎麼補。

這一張按票的一生（從哪來、狀態去哪看、怎麼關）排，每條仍然有效的決定、適用條件與例外都寫在同一處。本紙不改任何決定。

## 選項

每一題當時比較過的選項（全文在 `docs/archive/` 的舊紙）：
- 待辦：repo 裡的手寫待辦檔，或 GitHub issue。選 issue。
- 帶回的結論：①直接寫成決策紙或 cairn（經驗區）進 repo、外部原文只留連結；②另開 `docs/inbox/` 放外部原文，再由人挑出要升格的；③先開 issue，一句意圖加原文連結，不複製內容。選③。
- 狀態：手寫 `docs/next.md`；現算但不進主線；現算後提交回主線。選現算、不進主線。
- 頁面：產物只留在分支；用 GitHub Pages（GitHub 靜態頁面）掛固定網址。選固定網址。
- 人手關票：維持狀態頁紅字；票被關時查關票來源，沒有合進主線的合併請求就重開。選重開。
- 守衛漏了怎麼補：維持「守衛加狀態頁」；升成擋合併的規矩卡並准它上網讀 GitHub；要求人在版控裡留一份會漂的關票憑證。選規矩卡。

## 決定

**一、票從哪來：待辦與帶回的結論都進 GitHub issue，repo 不放手寫待辦檔。**（2026-09-09）
- 一件事一張 issue，不是一張卡一張。
- 暫緩的規矩卡按「在等什麼」分組，標 `deferred-cards`；內文只列卡 id（識別名）與等待條件，規格留在 `blueprint/cards-38.json`。
- 要拍板的題各開一張，標 `decision`。
- `handoff.md`（交接檔）只寫現在在哪與該看哪些 issue，不列待辦；不保留手寫的「下一步意圖」（舊狀態紙原本准的最多 20 行，同日被待辦紙收掉）。
- fork 出去、在外面產生的結論帶回時，先開一張 issue：一句「我想做這個」，加外部原文的連結或指向備份的路徑，不把內容複製進 repo。誰帶回來誰開（通常是指揮）。標籤照現有用法（`decision`、`deferred-cards`），或新的 `idea`。
- 帶回的結論以 issue 為唯一的入口，issue 也是它進度的所在。在 issue 裡討論；做了才落成決策紙（拍板）、cairn（經驗）或規矩卡（規矩），那支合併請求寫 `Closes #n`；不做就關掉，repo 一個字都不留（怎麼關見下面判斷 2）。

**二、狀態去哪看：由機器現算、不進主線，掛固定網頁。**
- 一支進版控的程式（住 `governance/status/`）從 git（版本控制）與 GitHub 現算：里程碑進度、開著的合併請求與 issue、每支檢查最近的結果、主線領先落後。里程碑與任務單由人放在 GitHub Milestones（里程碑）與 issues，位置由機器算。（2026-09-09）
- 開工時由 SessionStart hook（開工掛鉤）算一次、注入對話；每次併入主線由 CI（持續整合）算一次，推到只有機器寫的 `status` 分支（只有 `.github/workflows/status.yml` 寫它），歷史全留、不做 force push（強制改寫）、不排定時工作。
- 狀態程式產出 HTML（網頁檔），推到 `status` 分支；GitHub Pages 對著該分支根目錄提供固定網址 https://neknufelet.github.io/aosr-v3/ 。（2026-09-09 決定，2026-09-10 啟用）

**三、票怎麼關：只由合進主線的合併請求關，三層守。**（2026-09-10）
- 要關票，就在合併請求內文寫 `Closes #n`；GitHub 在那支合併請求合進主線時關票，並記下兩邊的連結。（決策票 #83）
- 決策類的題也照這條關：想關一張只需要寫紙的票，也得開一支合併請求把紙寫進去，靠那支合併請求關它；只改文件的決策票也一樣。討論後不做的票見下面判斷 2。
- 第一層，即時：`.github/workflows/issue-guard.yml` 在 `issues: [closed]` 事件叫起 `governance/status/issue_guard.py`，用 GraphQL（圖形查詢語言）的 `closedByPullRequestsReferences` 查關票來源，跟狀態頁共用查詢；有合進主線的合併請求就不動，沒有就用 `gh issue reopen` 重開並留言說明正確關法。`gh`（GitHub 命令列工具）不在、平台沒回應或資料形狀看不懂時，一律離開碼 2，不重開、不留言。
- 第二層，合併門口：規矩卡 `issues-closed-only-by-merged-pr` 擋合併（`declared_level = "blocking"`），掛在 `verify`；它逐張讀 GitHub 自己記的關票來源，不把票面上的互相提到當成落地；人手關的票超過 0 張就回 1。（決策票 #89）
  - 這是第二支准上網的檢查（第一支是 `merge-gate-read-back`）。每支例外各有一張紙、一筆 `[[settings.allow]]`，含 `reason` 與 `expires`，由 `exemptions-need-expiry` 守；這一筆到期日是 2026-12-08，缺席或過期就回 2 且不上網。准上網的檢查由「只准一支」改成兩支具名例外，沒有把通則放寬；第三支要不要放行必須另開紙。
  - 權限：這支檢查只讀關掉的票與掛著關票的合併請求；CI 自帶的 token（存取憑證）只給 `contents: read` 與 `issues: read`。重開票要的寫入權限只在守衛自己的 workflow（工作流程）：它宣告 `issues: write`（重開票要用）與 `contents: read`（checkout 拿程式碼要用）兩格；它是 repo 裡第一支會改 GitHub 狀態的機器，而且只有那份 workflow 擁有 `issues: write`。
  - 欄位名、查哪些格與「合併請求是否已落地」共用 `governance/status/collect.py`；只有主線分支名從卡的 `[settings]` 來，讓必紅樣本樹可以替換。
  - 具名放過某張票，寫在同一張放行表，必須帶票號、理由與到期日；過期視同沒放行。
- 第三層，事後：狀態頁顯示「關掉的票能不能串到綠的雲端收據」，守更長的鏈，不擋合併。
- 三層分工固定：守衛在事件發生時重開；規矩卡每次合併檢查重數並擋門；狀態頁顯示關票是否串到綠收據。

**跟舊紙字面不同、要靠判斷的兩處（不是原文搬移）**
1. 待辦紙（2026-09-09）寫「決策紙進 repo 後關票」，沒說怎麼關。關票規則（2026-09-10，#83）的原紙寫明「寫這張紙的那個 PR 就是關掉這一題的 PR」，合併後的關票紙代價段也寫「只改文件的決策票也必須用一個 PR 合入文件來關」。所以現行做法是：加入決策紙的那支合併請求內文寫 `Closes #n`，合併時關票。
2. 帶回結論的紙（2026-09-09）寫「不做就關掉，repo 一個字都不留」。#83（2026-09-10）之後沒有人手關票這條路，關票一定要有一支合進主線、內文寫 `Closes #n` 的合併請求，所以「一個字都不留」現在的意思是：外部原文與討論內容不進 repo 的任何檔案，但那支合併請求的內文與合併提交訊息會留下一行 `Closes #n`。用哪一支合併請求來關，舊紙沒有規定；主對話的做法建議是下一支交接檔或相關工作的合併請求。

## 為什麼

- 待辦與狀態不手寫：事故 `status-file-grows-into-history-ledger` 讓同一份進度檔同時寫「已併回」與「未併回」，還留下 37 條劃掉項目；事故 `index-docs-recopy-facts-that-drift` 是原始資料已經變了、手抄的文件沒變。待辦有票的開關狀態，狀態可以從版控與平台現算，兩者都不需要再抄一份會過期的檔。算出來的頁不進主線，但人仍要隨時看得到，所以用只有機器寫的分支掛固定網頁。
- 帶回的結論先開票：v2 事故 `decisions-live-only-in-conversation`，口述的修正沒落檔，對話清掉就丟，重述三四次；`moved-files-leave-dead-references`，帶回的原文放錯地方，搬走後引用全死。issue 有開關狀態、能討論、機器查得到；repo 只收有結果的東西，不會長出第二本 `docs/inbox/` 帳。原紙寫明跟「待辦走 issue」與「docs 三類」兩張紙對齊：前者已併進本紙，後者現由 `docs-four-classes-archive-for-superseded.md` 接手。
- 只由合進主線的合併請求關：上一代的事故形狀是「票關了，東西沒落地」。平台在合併時記下的關票來源可以回查，人的手寫憑證不行。即時守衛最快但依賴事件；合併門口的卡慢一步，卻每跑重數、不依賴事件；狀態頁不擋門，但看得到更長的收據鏈。三層各守一段，少一層就留一條漏路。

## 代價

- 離線看不到待辦，靠機器現算的狀態頁補；沒網路時開不了票。一個想法要多開一張票才能討論。
- 沒有開工掛鉤的工具，要手動跑一次狀態指令；舊 BASELINE 2.1.1 的 `docs/next.md` 做法不適用於這裡。
- repo 是公開的，狀態頁也公開；Pages 的啟用是 GitHub 設定，不在版控。
- 只改文件的決策票，也必須用一支合併請求合入文件來關。事件漏送或守衛壞掉時，票會暫時保持關閉，靠另外兩層補。
- 合併門口那支檢查與它的後設測試六個回合都依賴網路與 token；本機斷網跑 `uv run pytest` 時第一回合會紅（檢查回 2，而第一回合要 0）——雲端那一跑才算數、本機本來就只是宣稱，這是刻意接受的本機限制。准上網的檢查由一支變兩支。
- 一張票掛著上百個關票合併請求、一頁看不完時回 2；票變多查詢會變慢，但程式必須翻到底。立卡當天（2026-09-10）量到主線 22 張關閉票，每張都對得到合進主線的關票合併請求，人手關票 0；之後若雲端列出例外，處置是重開再由合併請求關，不是新增放行。
- 合成一張的代價：待辦、帶回的結論、狀態、關票在機器眼裡成為同一題；之後其中任何一部分要翻案，得取代整張，並把其餘仍有效的決定重帶一次。
