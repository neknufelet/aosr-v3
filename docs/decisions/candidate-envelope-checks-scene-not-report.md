# 候選包認「場景」不認「同一份報表」；各類自己帶自己的出身

## 問題

候選包（一個候選方案的全部分類評估）原本要求每一類的「出身」——哪一份報表、哪一支喇叭、哪一個接收點——跟外層逐字相同。可是四類吃的資料層級本來就不同：音色是一份報表、一支喇叭、一個點；聆聽區是一支喇叭、好幾個點；聲道匹配是好幾支喇叭、好幾個點，它的出身寫的是「多份報表」。同一個候選用正式入口產生音色與聲道匹配之後，原封不動裝不進同一個候選包（2026-09-21 局外終審 R2，票 #408）。現在各類分開都排得了名，只是因為每一支考卷一次只裝一類。

放著不管，之後真的四類一起排的時候，呼叫端只能去改寫出身才塞得進去——出身這一格就變成假的，追不回某個分數是哪一份報表算的。

## 選項

1. **A：候選包認場景。** 外層留候選代號與場景指紋；每一類帶場景指紋與自己的出身（單筆，或多筆留在各類自己的逐點來源裡）；候選包只檢查每一類的場景指紋等於外層。
2. **B：維持現狀。** 呼叫端裝包前把各類的出身統一改寫成外層那一份。

## 決定

採 A。

- **場景指紋由物理那一側給。** 三路接合報表的輸出有「場景」一節（票 #415）：同一個候選的每一份報表都一樣的輸入——房間、聲速、密度、各面牆的阻抗與散射、反射階數——的指紋。評估器只轉交，不自己算、也不收呼叫端另外貼的字串。
- **聲源與接收點座標不進場景指紋。** 左聲道與右聲道是兩份報表、聲源位置本來就不同，它們必須屬於同一個場景；擺位是不是同一套，由聲道組指紋與接收點相對佈局指紋（決策紙 `aggregate-identity-includes-upstream-and-layout.md`）守。
- **每一類評估多一格場景指紋。** 音色與殘響從報表拿；聆聽區與聲道匹配從它們疊的那幾份音色評估拿，批內不一致就整類不可彙總、原因指名是場景。
- **候選包外層＝候選代號＋場景指紋。** 不再有外層的出身，也不再逐條比對各類的出身；只檢查每一類的候選代號與場景指紋等於外層。各類自己的出身照舊留著：單一報表的類是那一份，疊很多份的類留總括的一筆、真正的逐點來源住在它自己的輸出裡。
- 排名輸出每一列原本抄外層的出身，改成抄場景指紋；各類的出身仍在每一類的評估裡。

## 為什麼

候選包要擋的是「別的房間、別的材料的結果混進來」，那是場景的事，不是「是不是同一份報表」。把檢查對準真正要守的東西，多份報表的類自然裝得進去，出身也不用造假。指紋由報表給而不是由呼叫端說，是因為呼叫端說的字串跟候選代號一樣只是一張貼紙；報表給的至少綁在它實際讀進去的輸入上。

## 代價

- 評估契約與排名輸出的形狀變更：候選包外層少一格出身、多一格場景指紋；每一類評估多一格場景指紋。交換格式版本怎麼跟著升記在票 #411。
- 求解結果的物件自己不記輸入，所以報表上的場景指紋目前只綁得到「組輸出時交進來的那一份輸入」，兩邊只核對得了反射階數；完整的綁定要動求解入口，記在票 #415 的留言。
- 引擎版本、物理常數設定檔、頻率軸不在場景指紋裡：它們不是報表的輸入，同一批候選本來就該用同一份；要不要另外守，等有第二個引擎版本同時存在時再問。
- 不走三路接合報表的評估（手造的輸入）要自己給一個場景指紋；考卷可以這樣做，產品路徑不行——這一條沒有機器在守，靠「正式轉接器只從報表拿」與審查。
